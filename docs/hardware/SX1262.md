# Waveshare SX1262 433/470M SPI/GNSS HAT на Orange Pi Zero 2W

Профиль предназначен для шилда на 40-контактной гребёнке Zero 2W. Модуль
приложения использует `wiringpi-zero2w` ABI v1 и Python `spidev`.
Для первого запуска подготовлен [профиль прямой LoRa-связи](../../config/opi-zero2w-sx1262.yaml)
с частотой 433,92 МГц. UART приёмника L76K доступен отдельно.

| Линия шилда | Физический контакт | H618 | Владелец |
|---|---:|---|---|
| MOSI / MISO / SCLK | 19 / 21 / 23 | PH7 / PH8 / PH6 | SPI1 |
| NSS / CS | 40 | PI3 | SPI ядра, логический CS0, активный LOW |
| RESET | 12 | PI1 | Python, выход с начальным HIGH |
| BUSY | 38 | PI4 | Python, вход |
| DIO1 | 36 | PC12 | Python, вход с событием по нарастающему фронту |
| DIO4 / TXEN | 31 | PI15 | Python, LOW при TX, HIGH при RX, LOW после операции |

Уровни DIO4 соответствуют методам отправки и приёма в примере производителя
`LoRaRF/SX126x.py`. Сам SX1262 дополнительно управляет DIO2. Время переключения и работу радиотракта предстоит измерить на конкретном шилде. [Схема Waveshare](https://files.waveshare.com/wiki/SX1262-XXXM-LoRaWAN-GNSS-HAT/SX1262_XXXM_LoRaWAN_HAT_sch.pdf) · [Официальный пример Waveshare](https://files.waveshare.com/wiki/SX1262-XXXM-LoRaWAN-GNSS-HAT/Sx126x_lorawan_hat_code.zip)

## Подготовка

Установите совпадающую `libwiringPi` и wheel в Python-окружение приложения.
Для существующего venv используйте `venv/bin/python -m pip install --no-index /путь/к/wiringpi_zero2w-0.1.0-py3-none-any.whl`.
Для `install.sh` путь к локальному wheel можно передать через
`WIRINGPI_ZERO2W_WHEEL`. Библиотека должна быть доступна загрузчику процесса.
[Сборка WiringPi и Python-пакета](https://github.com/shipmarty43/WiringPi/tree/3994de57b25201da906372abb51d063afc9dc9ea/python)

Из корня репозитория проверьте профиль и наложение на копии **штатного** DTB.
Для второй команды нужны утилиты пакета `device-tree-compiler`.

```sh
python3 core/main.py --config opi-zero2w-sx1262.yaml --check-config
python3 tests/check_sx1262_dtb.py /путь/к/sun50i-h618-orangepi-zero2w.dtb --dtbo /tmp/opi-zero2w-sx1262.dtbo
```

Для испытаний на плате установите проверенный DTBO как пользовательский оверлей
Armbian с именем `opi-zero2w-sx1262`. Этот профиль задаёт таблицу CS для SPI1
целиком. Перед включением сохраните текущую загрузочную конфигурацию и исключите
конфликтующие SPI1-оверлеи, включая старые `spidev_spi1_cs*`. Разные устройства
с `reg = <0>` на SPI1 могут помешать привязке драйвера. Для отката восстановите
прежний набор оверлеев и перезагрузите плату.

В форке armbian-config откройте **Device Tree Overlays → Waveshare SX1262**.
Там можно включить установленный DTBO, увидеть текущий узел SPI и выбор для
следующей загрузки, отключить оверлей и откатить сохранённое изменение.

Драйвер и служба LoRaWAN запрашивают общую блокировку ядра перед открытием
радио. Для отдельной установки драйвера на Armbian подготовьте её один раз.

```sh
sudo install -Dm644 hardware/overlays/opi-radio.conf /usr/local/lib/tmpfiles.d/opi-radio.conf
sudo systemd-tmpfiles --create /usr/local/lib/tmpfiles.d/opi-radio.conf
```

При установке от root на Zero 2W это делает `install.sh`. При выходе процесса
ядро освобождает блокировку. Владельца можно посмотреть командой
`armbian-config --api module_lorawan owner` в форке конфигуратора.

После загрузки приложение определяет номер шины по живому узлу `semtech,sx1262`
и проверяет контроллер, pinmux и активный LOW на PI3. Имя в `/dev` зависит от
ядра. Для платы с ядром без поддержки `armbian,spi-dev` потребуется соответствующая
привязка spidev. Пока приложение управляет радиомодулем, другие сервисы для
этого же шилда должны освободить его линии.

## Результаты без платы, 20 ноября 2026

- Оверлей применён к DTB образа Armbian `26.11.0-trunk.108`, ядро
  `6.18.57-current-sunxi64`. SHA-256 исходного DTB
  `4b90c01af0137b2297fb7243f200c5b32c33ce7e9b0e3d15fbde8c9733363758`.
  В итоговом дереве проверены PH6/7/8, CS0 на PI3 и 2 МГц. В файлах
  образа подтверждены `CONFIG_SPI_SPIDEV=y` и alias `armbian,spi-dev`.
- Хостовые тесты покрывают профиль, конфликт контактов/оверлеев, отсутствие
  радио, BUSY, сбой открытия SPI, отмену во время RESET, ошибку CRC, тайм-ауты,
  возврат уровней при ошибке и освобождение ресурсов. Проверяются команды
  TX/RX, длина и смещение данных из FIFO.
- В QEMU AArch64 с Python 3.14, ядром 6.18.57 и `gpio-sim` проверены реальные
  запросы GPIO, занятый RESET, отложенный фронт DIO1 и более 64 операций
  подряд. В тестах пакетов ответы SX1262 задаёт программная модель. Отдельный
  тест проводит транзакции через ARM64 `spidev` 3.6 и контроллер `spi-gpio`.
  При MISO, удерживаемом в LOW или HIGH, модуль отклоняет запуск.
  [Тесты](../../tests/test_sx1262.py) · [SPI для стенда QEMU](../../tests/sx1262-qemu-spi.dts)

Полный набор тестов на x86-64 дал 94 успешных и три пропуска для ARM64.
В исходной версии стенда все 15 тестов SX1262 прошли в ARM64-госте, включая эти три случая и загрузку
профиля штатным загрузчиком модулей. Для повтора на хосте используйте
`python3 -m pytest -q tests`. В архиве стенда выполните команду.

```sh
./run_sx1262_qemu.sh Image initramfs.gz gpio-sim.dts
```

Стенд использует одно ядро и 256 МиБ ОЗУ. Требуются `qemu-system-aarch64`,
`dtc`, `fdtoverlay` и `timeout`. В конце должен появиться `PASS-SX1262`.

После добавления общей блокировки повторный прогон на ядре с
`CONFIG_FILE_LOCKING=y` прошёл все 16 тестов гостевой системы. На хосте
проверена взаимная блокировка Python/C++ и освобождение радио после SIGKILL
каждого из процессов. Для нового прогона нужны обновлённые ядро и initramfs.

## Приёмка на плате

1. После загрузки подключённого шилда открыть **System Tools → Zero 2W GPIO
   header**. CS на 40 должен принадлежать ядру. Остановить другие клиенты
   этого радио до запуска аппаратного теста.
2. Запустить `./cyberdeck --config opi-zero2w-sx1262.yaml`. При старте драйвер
   делает RESET, ждёт BUSY и проверяет ответы GetStatus и GetPacketType.
   В журнале должен появиться переход в standby. При старте TX не выполняется.
3. С подключённой антенной обменяться известной короткой строкой в обоих
   направлениях со своим вторым LoRa-узлом. Параметры профиля по умолчанию —
   433,92 МГц, SF7, BW 125 кГц, CR 4/5, явный заголовок, CRC и преамбула 8.
   Сверить содержимое и длину. Проверить тайм-аут RX при выключенном втором узле.
4. При наличии анализатора сопоставить импульс RESET, активный LOW на NSS,
   BUSY, фронт DIO1 и уровень на 31 с транзакциями. После выхода проверить
   освобождение 12, 31, 36 и 38 и повторный запуск приложения.

Этот прогон относится к прямой LoRa-связи. Проверка совместимости с Meshtastic,
Reticulum и LoRaWAN ведётся на уровне соответствующих протокольных клиентов.

### Проверка без антенны на реальной Zero 2W, 2026-11-20

При отдельно подключённом Waveshare и остановленных радиослужбах выполните
из каталога проекта:

```sh
python3 tests/check_sx1262_board.py
python3 tests/check_sx1262_board.py --rx-irq
```

Первый запуск дважды проверяет RESET, standby, тип пакета LoRa и освобождение
четырёх GPIO и общей блокировки. Второй добавляет два коротких окна приёма.
Оба варианта ограничивают набор команд SPI и завершают работу в standby.

На ядре 6.18.57 два чтения GetStatus перед инициализацией вернули 0x22.
После инициализации на 2 МГц чип вернул GetStatus 0x22 и GetPacketType 0x01.
Таймер приёма поднял DIO1 (физический контакт 36) через 50,51 и 150,76 мс
для окон 50 и 150 мс. В обоих случаях GetIrqStatus вернул 0x0200, после
очистки линия опустилась. После каждого закрытия GPIO освободились, блокировка
была снова доступна. Проверка передачи и приёма пакета от второго узла остаётся
для стенда с антеннами.
